# Prisma Database Guide

How best to set up Prisma with Postgres (Neon or otherwise) on a new project. This assumes a standard Next.js project — the same approach works whether you're doing this by hand or asking an AI IDE to carry out a task that includes it.

## Before you start

You'll need a Postgres database to connect to — a Neon project works well, but nothing here is Neon-specific except one detail about connection pooling, noted below. You'll also want a single `.env` file at the root of the project for real values, and a committed `.env.example` alongside it that lists the same variable names with no real values in them. Next.js reads `.env` automatically, and so does Prisma's own CLI — there's no need for a second `.env.local` file duplicating the same values; one file covers both tools.

If you're on Neon specifically, always use the **pooled** connection string (the one with `-pooler` in the hostname) as your one and only `DATABASE_URL`. Don't add a separate `DIRECT_URL` and don't point Prisma at the non-pooler host — the pooled connection handles everything, including migrations, and adding a direct connection alongside it just gives you two things that can drift out of sync.

## Getting Prisma into the project

Start by installing Prisma and its client, then run its own init command to scaffold a schema file:

```bash
pnpm add prisma @prisma/client --save-exact
pnpm exec prisma init --datasource-provider postgresql
```

This creates `prisma/schema.prisma` and may write a `DATABASE_URL` line into a fresh `.env` for you. If you already have a `.env` with other values in it, just make sure the connection string ends up there rather than in a second file — and if `prisma init` added a `DIRECT_URL` field anywhere, remove it, since you're only using the pooled URL.

Open `schema.prisma` and confirm the datasource block looks like this, with no `directUrl`:

```prisma
generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider = "postgresql"
  url      = env("DATABASE_URL")
}
```

From here you can add your own models as usual — a `model User { … }` block, or whatever entities the project actually needs.

## A few scripts worth adding

It's worth adding a small set of scripts to `package.json` so the common Prisma commands are one word instead of a long flag-laden CLI call:

```json
{
  "scripts": {
    "postinstall": "prisma generate",
    "db:generate": "prisma generate",
    "db:migrate": "prisma migrate deploy",
    "db:push": "prisma db push",
    "db:studio": "prisma studio",
    "db:seed": "prisma db seed"
  },
  "prisma": {
    "seed": "tsx prisma/seed.ts"
  }
}
```

`db:push` is handy for quick prototyping, but it's not something to rely on for anything you're actually shipping — once a project is real, migrations become the source of truth, and `db:push` should stop being used against that database. One more thing worth knowing early: don't run `prisma migrate dev` against a pooled connection. It wants to create a temporary shadow database and take locks that connection pooling doesn't support, so it tends to fail in confusing ways. The alternative, covered next, works reliably against a pooler.

## Writing and applying your first migration

Rather than letting Prisma talk to a shadow database, you can generate the migration SQL directly by diffing against an empty starting point:

```bash
pnpm exec prisma migrate diff \
  --from-empty \
  --to-schema-datamodel prisma/schema.prisma \
  --script > prisma/migrations/$(date +%Y%m%d%H%M%S)_init/migration.sql
```

Alongside that new folder, add a small lock file Prisma expects, `prisma/migrations/migration_lock.toml`:

```toml
# Please do not edit this file manually
provider = "postgresql"
```

Then apply it:

```bash
pnpm db:migrate
```

That reads whatever's pending under `prisma/migrations/`, applies it to the database `DATABASE_URL` points at, and records what's been applied so it never repeats. Both `prisma/schema.prisma` and the `prisma/migrations/` folder should be committed to git — they're the durable record of what the database looks like, not throwaway output.

Later schema changes follow the same pattern — diff against what's already in `prisma/migrations/` instead of starting from empty:

```bash
pnpm exec prisma migrate diff \
  --from-migrations prisma/migrations \
  --to-schema-datamodel prisma/schema.prisma \
  --script > prisma/migrations/$(date +%Y%m%d%H%M%S)_describe_change/migration.sql
pnpm db:migrate
```

And in production — on Vercel or any CI environment — the same underlying command applies whatever's pending without prompting for anything:

```bash
pnpm exec prisma migrate deploy
```

Run that as part of your deploy step, before the app boots expecting new tables or columns to already exist.

## Using the client without exhausting connections

Instantiating `new PrismaClient()` in more than one place is the most common way a Next.js project quietly breaks in production — serverless environments spin up many short-lived instances, and each new client opens its own connection pool. The fix is a small singleton, usually placed at `lib/db.ts`:

```typescript
import { PrismaClient } from "@prisma/client";

const globalForPrisma = globalThis as unknown as { prisma?: PrismaClient };

export const prisma =
  globalForPrisma.prisma ??
  new PrismaClient({
    log: process.env.NODE_ENV === "development" ? ["error", "warn"] : ["error"],
  });

if (process.env.NODE_ENV !== "production") globalForPrisma.prisma = prisma;
```

Import `prisma` from this file wherever you need it on the server — Route Handlers, Server Components, standalone scripts. It should never be imported into a Client Component; database access only ever happens server-side.

## Seeding, if you need it

If the project benefits from some starting data, a seed script is a reasonable addition at `prisma/seed.ts`:

```typescript
import { PrismaClient } from "@prisma/client";

const prisma = new PrismaClient();

async function main() {
  // upsert on a unique field, so running this again later stays safe
}

main()
  .then(() => prisma.$disconnect())
  .catch(async (e) => {
    console.error(e);
    await prisma.$disconnect();
    process.exit(1);
  });
```

```bash
pnpm add -D tsx
pnpm db:seed
```

## If you're developing from WSL

This one's worth knowing before you hit it, rather than after: Neon's hostnames resolve to both an IPv4 and an IPv6 address, and WSL2 frequently has no working IPv6 route. Node's newer versions try IPv6 first by default and then hang rather than falling back quickly, which shows up as `fetch failed`, `ETIMEDOUT`, or Prisma's `P1001` ("can't reach database server") — specifically from WSL, while the exact same code works fine on macOS or in production on Vercel. It's not a sign anything is actually broken; it's a networking quirk of that one environment.

The most reliable fix is to tell Node to prefer IPv4 up front, at the very start of any script or server process that talks to the database:

```typescript
import { setDefaultResultOrder } from "node:dns";
import { setDefaultAutoSelectFamily } from "node:net";

setDefaultResultOrder("ipv4first");
setDefaultAutoSelectFamily(false);
```

If that's not enough — Prisma's default engine talks raw TCP rather than Node's `fetch`, so it doesn't always pick up the setting above — the same effect can be achieved by passing `NODE_OPTIONS='--dns-result-order=ipv4first --no-network-family-autoselection'` before whichever command is failing, or in the last resort by pinning the host to its IPv4 address directly in `/etc/hosts`. Whatever you do, don't reach for rotating the database password as a fix — this has nothing to do with credentials, only with which network route gets tried first.

## Day to day

Once everything above is in place, the routine commands are: `pnpm db:migrate` to apply pending migrations (locally or in production), `prisma migrate diff` followed by a deploy to author a new one, `pnpm db:generate` to refresh the client after pulling schema changes from elsewhere, `pnpm db:studio` to browse the data visually, and `pnpm db:seed` if a seed script exists. Every time the schema changes, commit both `schema.prisma` and the new migration folder together — they're one change, not two.
